# Contributing to DLOFeel-State

Acronyms used below: DLO (deformable linear object), CLI (command-line interface),
FP32 (IEEE single precision), TF32 (NVIDIA 19-bit-mantissa tensor-core format), ViT
(vision transformer), K (number of predicted shape vertices).

## Scope of this repository

This is the research code release accompanying a paper that is under review. Its job
is to let a reader re-run, inspect, and build on the results in that paper, so
reproducibility outranks everything else here. The concrete expression of that
priority is the parity gate in `tests/test_parity.py` (section 3): every change has to
keep it green.

Welcome:

- bug fixes, portability fixes, clearer documentation
- new experiments that build on the released model (section 5)
- tests that pin numerics or widen platform coverage

Not welcome:

- style, typing, or modernization passes over the ported research code (section 4)
- changes that move the published numbers without saying so in the pull request

Contributions are accepted under this repository's own licence, MIT, see
[LICENSE](LICENSE). The Sparsh submodule under `third_party/` is a separate
third-party work and is out of scope for changes here, see [NOTICE](NOTICE).

## 1. Development setup

Python >= 3.12. The Sparsh tactile encoder is consumed as a git submodule and is not
redistributed, so the clone has to pull submodules:

```bash
git clone --recurse-submodules <repo-url>
cd dlofeel-state
uv venv
uv pip install -e .
uv pip install --group dev      # pytest, ruff, pre-commit
pre-commit install
```

Already cloned without submodules? Run `git submodule update --init --recursive`.

`pre-commit install` wires the ruff lint and format hooks declared in
`.pre-commit-config.yaml`. They read their rules from `pyproject.toml`, so the hooks
and a manual `ruff` run agree (section 4).

The dataset and the released checkpoint are not in git. [docs/DATA.md](docs/DATA.md)
covers how to get them and where to stage them; [docs/training.md](docs/training.md) is
the flag reference for the two console scripts.

## 2. Running the tests

```bash
pytest -q
```

The suite needs no dataset download. The only data in git is the 8-frame fixture under
`tests/fixtures/parity/`, so a clean checkout gives **35 passed, 3 skipped** in about a
minute. The three skips are the checkpoint-gated tests:

| Test | What it gates |
|---|---|
| `tests/test_parity.py` | numeric parity of the packaged `evaluate()` against the golden snapshot |
| `tests/test_eval_cli.py` | the same golden, reached through the `dlofeel-eval` CLI and its typed config |
| `tests/test_model_loads_ckpt.py` | strict `state_dict` load of the released K = 16 checkpoint |

Each reads the checkpoint path from `DLOFEEL_PARITY_CKPT` and skips when it is unset,
because the 137 MB checkpoint is not committed. Point it at the released `best.pt` to
run the full **38 passed**:

```bash
export DLOFEEL_PARITY_CKPT=/path/to/k16/best.pt
pytest -v
```

Those three tests use CUDA when torch finds it and fall back to CPU otherwise. The
tolerance below was validated on CUDA, so treat a CPU-only failure as uncharacterized
rather than as a regression, and mention the platform in the issue or pull request.

## 3. The parity gate is the one hard rule

`tests/test_parity.py` is not a smoke test. It reconstructs the released inference path
and compares it against a snapshot that predates the port:

1. loads the K = 16 checkpoint named by `DLOFEEL_PARITY_CKPT`, plus that checkpoint's
   own config from `tests/fixtures/parity/config.yaml`;
2. repoints the two path-valued config keys (`norm_stats_path`, `blank_ref_root`) at
   the self-contained fixture copies and blanks the Sparsh pretrained-weights path,
   since `best.pt` supplies every ViT weight through a strict load;
3. runs the packaged `evaluate()` over the 8 committed frames in
   `tests/fixtures/parity/samples/` with `batch_size=8`;
4. asserts the predictions and the loaded ground truth match
   `tests/fixtures/parity/golden_preds.h5` within `atol=1e-5`.

That golden snapshot was generated by the original research codebase before any code
was ported, so the target was fixed in advance and this repository cannot quietly
redefine it. `tests/test_eval_cli.py` repeats the comparison through the CLI surface.

**The rule.** A pull request that touches the model, the loss, the data pipeline, or
eval numerics has to keep both gates green. Moving the numbers is a research change,
not a refactor: it needs a deliberately regenerated golden, the provenance recorded in
`tests/fixtures/parity/README.md`, and an explicit note in the pull request. Never
loosen `atol` to make a diff pass.

**The TF32 caveat.** The golden was produced in full FP32 under torch 2.10. Newer torch
enables TF32 for cuDNN convolutions by default, and that alone shifts the predictions of
the Sparsh ViT patch-embed convolution by roughly 4e-5, without a single line of code
changing. Both parity tests therefore pin FP32 before touching torch:

```python
torch.backends.cuda.matmul.allow_tf32 = False
torch.backends.cudnn.allow_tf32 = False
```

With those pins the port reproduces the golden to about 3e-8, three orders of magnitude
inside the gate. Leave them in place. Removing them turns the gate into a test of the
local CUDA toolchain instead of a test of this code.

## 4. Lint and format

```bash
ruff check src scripts experiments tests    # exits 0
ruff format .                               # or: ruff format <the files you added>
```

Both are clean on a fresh checkout and are expected to stay that way. `pre-commit run
--all-files` runs the same two tools.

**Ported code keeps its original style.** Most of `src/dlofeel_state/{data,engine,losses,models,viz}/`,
`scripts/`, and `experiments/` is a port of the frozen research codebase that produced
the paper's numbers, and the parity gate is the contract those files answer to. Their
lint findings are inherited, not introduced: running ruff over the original sources
reports the same codes. So they are suppressed rather than fixed, per file and per rule,
in `[tool.ruff.lint.per-file-ignores]` in `pyproject.toml` (33 files, 160 findings at the
ruff 0.16.0 baseline), and the same paths are excluded from the formatter in
`[tool.ruff.format]`.

Do not "fix" them. Re-sorting the imports in `data/dataset.py` buys nothing and costs the
line-for-line correspondence with the code that produced the published results, which is
what makes the port auditable. Two consequences for contributors:

- If a newer ruff reports a new code in a ported file, add that code to the file's entry
  in `per-file-ignores` with a comment, rather than editing the file.
- Files you add are not covered by any of it. New code gets the full rule set and is
  expected to be lint-clean and formatted.

The hooks pin ruff v0.16.0, the release the baseline was calibrated against. Releases
older than 0.9 reject the baseline outright, since they do not know some of the rule
codes it names.

One inherited finding is worth knowing about: `data/transforms.py` uses `List` in an
annotation it never imports (`F821`). It sits on a path the parity gate does not
exercise, and it is left for a separate, deliberate fix rather than folded into an
unrelated pull request.

## 5. Adding an experiment

Experiments are organized one directory per paper artifact, `experiments/<paper-artifact>/`,
as listed in the reproduction table in the [README](README.md). To add one:

1. Create `experiments/<paper-artifact>/` and put the driver there. Follow the shape of
   the existing directories: a `run_*.sh` that pins the arms of the study and a `.py`
   driver for anything the console scripts cannot express alone.
2. Drive training and evaluation through the installed console scripts, `dlofeel-train`
   and `dlofeel-eval`, not by importing engine internals. They are the typed draccus
   entrypoints (`TrainConfig`, `EvalConfig`), so a run is fully described by its flags,
   and [docs/training.md](docs/training.md) already documents them.
3. Keep every path repo-root-relative and let the script `cd` to the repository root.
   `tests/test_paths_relative.py` fails on machine-specific absolute paths in anything
   under `src/`, `scripts/`, or `experiments/`.
4. Add a dry-run test to `tests/test_experiments_dryrun.py`. Register a CLI driver in
   its `HELP_DRIVERS` list, which asserts `python <driver> --help` exits 0 and so proves
   the whole import chain and the parser resolve without touching data, a checkpoint, or
   a GPU. For a library-style driver with no CLI, add an `importlib` import test
   alongside the existing one.
5. Run `ruff check src scripts experiments tests` and `pytest -q` before opening the
   pull request.

Experiment results, checkpoints, and figures do not belong in git. Ship the driver and
the recipe, and point at the released artifacts.
